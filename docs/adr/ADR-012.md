# ADR-012 - Premium Windows App Shell

Status: Accepted
Research classification: Inferred from documented platform, CLI, release, and
dependency decisions plus user-supplied licensed asset evidence
Source:
`WasteLandForge/research/Wasteland Forge Platform Architecture & System Design-deep-research-report.md`,
`WasteLandForge/research/R006 Developer Experience and CLI Workflow Model for WastelandForge-deep-research-report.md`,
`WasteLandForge/research/WastelandForge Validation Testing CI Release and Governance-deep-research-report.md`,
Unity Asset Store Terms/EULA, and user-provided Heat 1.1.8 ownership evidence

## Decision

WastelandForge will add a premium Windows desktop app shell named
`WastelandForge.exe`.

The app shell will be built as a Unity desktop application using the licensed
Heat - Complete Modern UI 1.1.8 kit as its first visual system. The app shell
will not replace the Forge CLI or the deterministic Forge core. It will present
Forge workflows through a polished project dashboard, wizards, status views,
report views, and advanced logs while running `forge.exe` as the backend worker
for the first implementation slice.

The first backend bridge is:

```text
forge.exe --version
forge.exe capabilities list --format json
forge.exe validate <project-root> --format json
```

The GUI consumes stable machine-readable Forge output. It must not parse
human-oriented console text as the correctness path.

## Consequences

- `forge.exe` remains the stable automation interface for CI, scripts, editor
  tasks, and power users.
- The app shell is a presentation and orchestration layer over Forge behavior,
  not a second source of validation, build, capability, or release truth.
- Canonical project truth remains versioned YAML/JSON source contracts in the
  repository.
- The app shell must preserve offline-first and AI-optional correctness.
- The app shell must not introduce undocumented Forge command aliases.
- Heat source assets must not be committed to the public repository or
  redistributed as a raw reusable asset pack.
- Heat-derived app assets may only be distributed as embedded components of
  the compiled WastelandForge app, subject to license and attribution checks.
- The licensed Unity/Heat app shell is not a hard requirement for WastelandForge
  core contribution, validation, build, or release verification.

## First MVP Surface

The first premium app shell should include:

- branded splash and application chrome,
- project selector,
- Doctor and capability dashboard,
- validation report view,
- advanced log panel,
- settings for local project, game root, Data root, and tool paths.

The app may expose terminal-equivalent details in advanced views, but raw
console output must not be the first-run product experience.

## Asset And License Boundary

The Heat kit is treated as a licensed local asset input for the app-shell build,
not as repository source truth. The app-shell lane must complete an asset audit
before any asset is copied into a build tree or release package.

Minimum audit checks:

- confirm the asset is not marked Restricted Asset on the Asset Store page,
- record Unity Asset Store license tier and seat coverage,
- record any third-party notices required by the kit readme,
- handle CC BY 3.0 controller graphic attribution if those graphics ship,
- avoid AI/ML training, dataset use, scraping, or asset extraction workflows,
- ensure end users cannot access the Heat kit as a reusable source asset pack.

## Gate Impact

Gate 312 remains routed to `forge init` project scaffold planning. Gate 313
starts the premium Windows app shell planning lane unless maintainers explicitly
choose to run that lane in parallel.

Later app-shell gates should cover:

- Unity app-shell repository layout,
- licensed asset import policy,
- app-to-CLI process bridge,
- JSON report contracts consumed by the app,
- first-run setup wizard,
- Doctor/capability dashboard,
- validation report view,
- installer packaging,
- signing, update, and release evidence.

## Open Checks

- Unity editor/runtime version for the app-shell build.
- Whether the Unity project lives in this repository or a sibling/private asset
  workspace with deterministic export back into this repository.
- Installer technology and update channel.
- Code signing and release provenance model for the Windows app.
- CI strategy for Unity builds without making Unity a hard dependency of core
  CLI validation.
- Exact Heat attribution bundle and third-party notice text.
