# WastelandForge Generator and Build Pipeline Architecture

## Executive conclusion

The evidence supports a clear recommendation for **ADR-009**: WastelandForge should use a **deterministic, capability-aware build graph** in which canonical registry documents are the only source of truth and every downstream artefact is disposable and rebuildable. That recommendation is strongly aligned with the standards and toolchains around it: JSON Schema Draft 2020-12 is explicitly intended for validation, documentation and annotation; JsonSchema.Net’s own guidance is “build once; evaluate many times” and it can return structured validation results with errors and annotations; MSBuild’s incremental model is built around explicit inputs and outputs; and the Reproducible Builds project defines reproducibility as recreating bit-for-bit identical artefacts from the same source, environment and instructions. citeturn23view1turn23view2turn12view0turn12view1turn12view2turn13view2

For **v0.1**, the safest and highest-value outputs are deterministic text and metadata artefacts: generated documentation, schema/reference pages, dependency and capability reports, build manifests, provenance files, and package metadata. The next step after that should be **capability-gated support outputs** such as **MCM Extender JSON** and carefully bounded **JIP LN text scripts**. High-risk binary plugin generation or patching should be deferred. xEdit’s documentation explicitly positions the tool around conflict resolution, cleaning and scripting, but also says extensive mod changes are generally better handled in the Creation Kit/GECK; by contrast, MCM Extender is explicitly designed for script-free JSON menus, and JIP LN exposes a documented text-script runner surface. citeturn4view4turn18view0turn5view0turn19search2turn4view5

That means WastelandForge should become a **generator-and-orchestrator platform**, not a GECK replacement, not an xEdit replacement, and not a generic “ESP compiler”. Its job is to turn validated intent into repeatable artefacts, call out missing capabilities before generation begins, record exactly how an output was produced, and keep the authoring surface in version-controlled registry files rather than in hand-edited generated state. citeturn12view2turn13view2turn14view0

## What the ecosystem and standards imply

JSON Schema is a particularly good fit for WastelandForge’s generator layer because the specification is not only about assertions; it is also about documentation, annotation, hyperlink navigation and interaction control. The 2020-12 core specification formalises dialects and vocabularies, distinguishes assertions from annotations, and states that unrecognised individual keywords should be treated as annotations. In practice, that gives Forge a standards-based place to store validation rules, human-facing schema metadata, and non-authoritative generation hints without making generated outputs canonical truth. JsonSchema.Net mirrors that model: it supports Draft 2020-12, exposes configurable output formats, preserves annotations when asked, and returns validation results that include both errors and annotations. citeturn23view1turn23view2turn12view0turn12view1

The New Vegas ecosystem also pushes the design toward an explicit capability model because provider surfaces are **heterogeneous by install scope**. xNVSE must be copied into the **game root** alongside `FalloutNV.exe`, and its own README says **not** to copy it into `Data` or install it with MO2 like a normal mod. ShowOff, by contrast, expects its DLL and INI under `Data\nvse\plugins`. JIP LN’s Script Runner scans `Data\nvse\plugins\scripts` and executes files with lifecycle prefixes such as `gr_`, `gl_`, `gs_`, `gx_`, `gn_`, and `ln_`. MCM Extender installs like a normal mod but depends on an entire runtime stack: MCM, xNVSE, JIP LN, JohnnyGuitar, ShowOff and UIO. UIO itself is explicitly designed to manage UI/HUD extensions, detect and prevent UI issues, and keep the UI intact. A build system that treats “dependency installed” as a single boolean will miss essential differences in **root**, **data-managed**, **runtime-session**, and **tool/editor** scope. citeturn4view3turn16view0turn4view5turn5view0turn4view1

The ecosystem also provides both **offline** and **runtime** ways to reason about capabilities. `GetNVSEVersion` returns the installed xNVSE version, while `GetPluginVersion` returns the version of a loaded NVSE plugin and uses the registered plugin name rather than the file name. That makes runtime enrichment possible, but it does not remove the need for local/offline detection, because build commands must still work before a play session starts. In other words, R006 should treat runtime checks as **enrichment**, not as the only source of capability truth. citeturn19search0turn19search1

Version-aware provider modelling is also necessary because the FNV extender stack is still moving. As of June 2026, the xNVSE repository shows **6.4.8** as the latest release, JohnnyGuitarNVSE shows **5.28**, and ShowOff shows **1.84**. That is exactly the kind of live version churn that makes capability resolution part of the build plan itself, not just a pre-flight note in a README. Forge’s build cache and provenance model should therefore key off **resolved provider versions**, not merely presence/absence. citeturn4view3turn16view1turn16view0

One additional standards observation matters for implementation strategy. If Forge later wants strongly typed generator models and canonical JSON serialisation at build time, **Corvus.JsonSchema** is a credible future extension because it explicitly advertises full Draft 4 through 2020-12 validation, Roslyn incremental source generation, and RFC 8785 JSON Canonicalization support. That does **not** make it necessary for v0.1, but it does mean the architecture can be designed now so that validator-first and typed-model paths remain compatible later. citeturn20view0

## Recommended build graph

The recommended build graph is:

```text
Source registries
  → normalisation to canonical JSON graph
  → schema validation
  → semantic validation
  → capability resolution
  → build planning
  → generator execution
  → post-generation validation
  → provenance manifest
  → staging
  → package / release
```

That shape is not just tidy architecture; it matches how the underlying standards want to be used. JSON Schema and JsonSchema.Net both assume a model where schemas are built and then repeatedly evaluated, while MSBuild’s incremental execution model depends on declared inputs and outputs and can skip fully or partially up-to-date targets. WastelandForge should adopt the same discipline even if it implements its own planner rather than reusing MSBuild directly. citeturn23view2turn12view1turn12view2turn12view3

The key new component in R006 is the **build planner**. It should not merely “run all generators”; it should compute a dependency graph over source files, resolved registries, resolved capabilities, generator manifests and outputs. At minimum, each generator node should be invalidated when any of the following change: an input file digest, the generator version, the effective schema version used to validate the relevant inputs, or the resolved capability set for that generator’s declared requirements. MSBuild’s documentation uses timestamps and explicit input/output mappings to decide whether a target is stale; Reproducible Builds guidance then extends that thinking by tying correctness to the full source, environment and instruction set, and by recommending cryptographic checksums when comparing artefacts. Forge should therefore use **hash-based build state** for its own planner even if some external tools remain timestamp-oriented. citeturn12view2turn13view2

A practical consequence is that **generator contracts need to be first-class data**. Every generator should declare its input registry kinds, optional and required capabilities, output paths and types, whether it is deterministic, whether an output is safe to clean, whether external validation is required, and whether human review is recommended. JSON Schema’s vocabulary and annotation model is well suited to describing those contracts, and JsonSchema.Net already has the evaluation output machinery that a Forge validator would want for transparent diagnostics. citeturn23view1turn12view0turn23view2

The command boundary should follow the graph boundary. `forge validate` should stop before generation. `forge generate` should produce generated artefacts and provenance. `forge build` should run the full pipeline through post-generation validation. `forge package` should assemble a distributable staging tree. `forge release` should publish or prepare release assets. GitHub’s own model maps well to this split: Actions artifacts are for build outputs produced by a workflow run, while Releases are deployable iterations tied to repository tags and released assets. citeturn22view0turn22view1turn22view2

## Generator scope for v0.1

The strongest evidence-backed **v0.1 generator targets** are deterministic text artefacts and support files. These include registry reference documentation, schema reference documentation, capability and dependency matrices, validation rule pages, build manifests, package manifests, release summaries, and machine-readable reports such as JSON and SARIF. They are easy to diff, easy to hash, easy to clean, and easy to regenerate. They also fit JSON Schema’s stated uses for validation and documentation, and they align with GitHub Actions’ notion of an artefact as a file or collection of files produced by a build. citeturn23view1turn22view1turn14view0

The best **early game-support generator** is **MCM Extender JSON**. MCM Extender explicitly says mod authors can create feature-rich MCMs “entirely from JSON files”, that those menus can be script-free, and that no ESP/ESM is required for a mod to have its own dedicated MCM. It also says the framework natively handles saving settings to INIs, updating game variables and running script functions, while remaining backwards compatible with existing MCM. That is almost ideal generator surface area for Forge: structured input, deterministic text output, clear downstream provider requirements, and a concrete benefit for mod authors without touching binary plugin records. citeturn5view0turn5view1

**JIP LN text script generation** should be treated as a second-wave feature rather than the first default output. The Script Runner is attractive because it gives Forge a documented text-based injection surface tied to game events, but it comes with non-trivial constraints: scripts live in a specific directory, are triggered by filename prefixes, are run in the console environment, cannot exceed **16,384 bytes**, and do not resolve Editor IDs by default. The documentation also explains that authors often need JohnnyGuitar or explicit `BuildRef` patterns to bridge from stable mod data into callable runtime logic. That makes JIP script generation viable, but only when the generator is explicit about event prefixes, size budgeting, provider requirements and FormID-resolution strategy. citeturn4view5turn16view1

**xEdit script generation** is worthwhile, but the role should stay narrow. xEdit implements a Pascal-based scripting engine with functions for interacting with editor elements, including finding records and fixing conflicts. Its broader manual also says xEdit is valuable for standardisation, cleaning and conflict work, while warning that extensive mod changes are generally better done in the Creation Kit/GECK. The right conclusion is that Forge should generate **audit scripts, inspection scripts, scaffolds and report parsers** for xEdit, not use xEdit as a silent backend for high-risk patch authoring. citeturn18view0turn4view4

High-risk outputs should be **deferred**. That includes ESP/ESM binary generation, record merge patches, dialogue record rewrites, quest patching, navmesh edits, cell/worldspace edits and complex conflict-fixing patches. The reason is not that these are impossible; it is that the evidence base points the other way for v0.1. xEdit still treats those areas as record-aware human work, GECK remains the official editing environment, and the modding workflow around conflicts and patches is still heavily judgement-based. WastelandForge should not spend its first milestone competing with those tools in their riskiest domain. citeturn4view4turn18view1turn4view2

Packaging should also be staged carefully. The STEP FOMOD guide shows that FOMOD is effectively a separate XML installer language with required `fomod` structure, `info.xml`, `ModuleConfig.xml`, manager-specific behaviour, and testing expectations. That complexity makes FOMOD a good adapter target later, but not a foundation for the initial build pipeline. The v0.1 packaging target should therefore be a **plain deterministic ZIP staging tree plus metadata**, with FOMOD generation added later as a specialised packaging adapter. citeturn21view0turn21view1turn22view0

## Provenance reproducibility and safety

Reproducibility should be a first-class design goal, not a polish task. The Reproducible Builds definition says a build is reproducible when the same source code, build environment and build instructions recreate bit-for-bit identical artefacts, and it recommends cryptographic checksums for comparison. The same body of guidance also warns that timestamps, archive metadata, file ordering and similar hidden inputs routinely break reproducibility. For Forge, that means provenance is not optional bookkeeping; it is part of the build contract itself. citeturn13view2turn13view3turn24view1

The mandatory local output of every successful build should therefore be a **build manifest**. At minimum it should record the project identifier, Forge version, generator identities and versions, resolved capability set, source digests, schema versions, output digests, and a reproducible build timestamp derived from source state rather than from wall-clock time when making release-grade artefacts. The `SOURCE_DATE_EPOCH` convention is specifically designed for this purpose, and the Reproducible Builds documentation explicitly recommends using it instead of embedding the current date and time. For Forge’s own .NET binaries, Microsoft’s `Deterministic` and `ContinuousIntegrationBuild` settings are also directly relevant because they target byte-for-byte equivalent compiler output and normalised file paths in CI builds. citeturn24view0turn24view1turn13view0turn13view1

GitHub’s hosted provenance features are useful, but they should be treated as **additional attestation**, not as the only provenance record. Actions artifacts can persist build outputs between jobs, and GitHub’s artifact attestations can generate cryptographically signed provenance that ties an artefact to the workflow, repository, commit SHA and triggering context. That is an excellent later integration for public releases. The mandatory baseline, however, should remain a **local Forge build manifest** that exists even when the project is built entirely offline. citeturn22view1

Forge should also adopt a strict directory safety policy. Generated outputs should live under a dedicated `generated/` tree, packaged distributables under `dist/`, and canonical source under `src/` or equivalent. Cleaning should default to generated artefacts only. Generated text files should carry short headers saying they were produced by WastelandForge, while binary artefacts should use **sidecar provenance files** rather than risky in-band modification. This recommendation follows directly from the generated-file handling guidance in MSBuild and from reproducible-builds guidance on archive metadata and timestamp normalisation. citeturn12view3turn13view3turn24view1

For packaged archives specifically, deterministic assembly matters. Reproducible Builds documentation calls out file ordering, modification times and other archive metadata as common sources of drift, and even shows deterministic ZIP/TAR construction patterns. Forge should therefore sort staged files before archiving, clamp mtimes from `SOURCE_DATE_EPOCH` or a source-derived revision date, and record final package digests in the build manifest. Without that, “rebuildable” packages will still be difficult to verify. citeturn13view3turn24view0

## Capability gating integrations and diagnostics

Capability gating is not a nice-to-have; it is a direct consequence of the provider landscape. A generator that targets MCM Extender JSON is really targeting a stack that includes MCM, xNVSE, JIP LN, JohnnyGuitar, ShowOff and UIO. A generator that targets JIP text scripts depends on JIP LN, and may also depend on JohnnyGuitar or specific FormID-resolution strategies. A generator that emits xEdit scripts depends on the xEdit toolchain but not on a runtime session. R006 should therefore make every generator declare **required capabilities**, **optional capabilities**, and **fallback behaviour** up front. citeturn5view0turn4view5turn18view0

The MCM path is the clearest example of how this should work. If the project asks for generated MCM JSON and the required UI/runtime capabilities are present, Forge should generate the JSON and validate it. If that stack is missing, Forge should either fail clearly or fall back to a simpler configuration surface such as an INI template, depending on the project’s declared policy. UIO’s own role as an organiser and conflict-prevention layer for UI/HUD extensions makes it especially sensible to model MCM generation as **capability-gated and UI-aware** rather than as a blind file dump. citeturn5view0turn4view1

The xEdit and MO2 boundary should also stay clean. xEdit’s “The Method” documentation assumes that newly made patches often land in MO2’s **overwrite** folder and explicitly says it is bad practice to leave plugins there, recommending that the author create a dedicated mod from overwrite instead. That is a valuable lesson for Forge integration design: if Forge ever writes outputs into an MO2-managed workflow, it should materialise them as **named output mods/workspaces**, not as anonymous clutter in overwrite. citeturn18view1

Diagnostics should be structured enough to feed terminal output, machine-readable JSON and SARIF. OASIS describes SARIF as a standard output format for static analysis tools intended to make results easier to view, understand, compare and manage across tools. That maps almost perfectly to Forge’s WF-GEN diagnostic family: missing generator inputs, required capability absent, fallback used, stale output, unsafe overwrite refused, provenance missing, output validation failed, or external-tool validation failed. A human-readable CLI message is still necessary, but the canonical diagnostic shape should be structured. citeturn14view0

The release boundary should be equally explicit. GitHub Actions artifacts are a good match for intermediate build outputs and logs; GitHub Releases are a good match for tagged, user-facing deliverables and release assets; and GitHub’s REST API can create releases and upload release assets programmatically. So the architectural split should be: **build artefacts first, release assets later**. Forge should never confuse “available for download” with “source of truth”. citeturn22view0turn22view1turn22view2

## ADR recommendation and MVP slice

The recommended decision is:

> **ADR-009 — Deterministic Generation and Build Pipeline**  
> WastelandForge generates downstream artefacts from canonical registry source through a deterministic, capability-aware build graph. Generated outputs are never canonical truth. Every generated artefact must be traceable to source inputs, schema versions, Forge version, capability resolution and generator version.

That recommendation is supported by the structure of JSON Schema 2020-12, the evaluation model exposed by JsonSchema.Net, the input/output discipline of MSBuild incremental generation, the reproducibility guidance around timestamps and archive metadata, and the real install-scope/provider differences in the FNV toolchain. citeturn23view1turn23view2turn12view2turn24view1turn4view3turn16view0turn4view5

A strong **MVP slice** after this research would consist of five implementation packages: `WastelandForge.Generation`, `WastelandForge.Build`, `WastelandForge.Provenance`, `WastelandForge.Validation`, and `WastelandForge.Cli`. The first real generators should be registry and schema documentation, capability and dependency reports, a mandatory `build-manifest.json`, and deterministic package staging. **MCM Extender JSON** is the best first game-facing generator. **JIP LN script generation** should remain opt-in until capability contracts and runtime assumptions are more mature. **xEdit** should start as an audit/orchestration adapter, not a patching backend. citeturn5view0turn4view5turn18view0turn4view4

The minimum useful command surface is straightforward:

```bash
forge validate ./ExampleMod
forge generate ./ExampleMod
forge docs ./ExampleMod
forge build ./ExampleMod
forge package ./ExampleMod
forge clean ./ExampleMod --generated
```

That command design is justified by the evidence above: validation should be separable from generation, generation should be separable from packaging, and packaging should be separable from release transport. GitHub’s distinction between workflow artefacts and tagged releases reinforces the same boundary at the CI/CD layer. citeturn22view0turn22view1

The final boundary to keep is the **offline-first, AI-optional** one. Nothing in the recommended v0.1 chain requires cloud execution: schema validation is local, xNVSE and its plugin ecosystem are local files and local runtime functions, JIP Script Runner is a local directory scan, xEdit scripting is local Pascal, and GitHub publication is an optional downstream step rather than a correctness dependency. AI can later help explain diagnostics or draft release notes, but the correctness path should remain fully deterministic and local-first. citeturn23view2turn4view3turn4view5turn18view0turn22view0turn22view1

The remaining open questions are mostly about **sequencing**, not fundamentals: whether MCM JSON ships in v0.1 or v0.2; whether JIP script generation should wait for stronger runtime contracts; whether generated documentation belongs in Git or only in build artefacts; and when FOMOD support becomes worth its own adapter. None of those questions change the main conclusion. The main conclusion is already well supported: WastelandForge should not try to be a magical ESP compiler. It should become a deterministic build platform that knows **what** to generate, **why** it was generated, **which capabilities were required**, and **how to rebuild it safely**. citeturn21view0turn12view2turn13view2
