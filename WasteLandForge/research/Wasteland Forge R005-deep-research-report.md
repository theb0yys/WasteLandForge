# Wasteland Forge R005

## Executive finding

The strongest conclusion from current evidence is that **ADR-005 should resolve to C: Platform Layer**, but only in a constrained form: **AI generates, Forge validates, humans approve**. That conclusion is not just a philosophical preference. It matches how current agent toolkits are actually designed: approvals, guardrails, tracing, resumable state, and evaluation loops are treated as first-class features rather than optional extras. OpenAI’s agents guidance explicitly distinguishes automatic guardrails from human review, recommends pausing before sensitive actions, and treats tracing and evaluation as core to production workflows. LangGraph similarly centres durable execution, human-in-the-loop interrupts, persistence, and long-term memory for stateful systems. NIST’s Generative AI Profile likewise frames governance, provenance, pre-deployment testing, and incident management as foundational controls rather than afterthoughts. citeturn27view0turn27view1turn28view0turn28view1turn28view2turn26view0

The practical implication for Wasteland Forge is that AI should not be bolted on as a chat helper at the edges of the toolchain, and it should not be trusted as an autonomous author either. It should sit **inside the architecture** as a governed generation layer that outputs typed artefacts into a validation and review pipeline. That framing is also consistent with current open-source engineering norms: GitHub’s own Copilot guidance says AI code review should *supplement* rather than replace human review; its agent documentation warns that generated code may be inaccurate, insecure, biased, or a near match for public code; and the Linux kernel now formalises that only humans may certify contributions, with AI assistance disclosed via an `Assisted-by` trailer and the human submitter retaining full responsibility. citeturn24view2turn24view3turn24view4turn25view1turn8search2

For Wasteland Forge, that means the platform should own four things directly. **Generate:** dialogue drafts, quest skeletons, manifest files, validators, tests, changelogs, and documentation scaffolds. **Validate:** schema correctness, lore consistency, dependency expectations, rights metadata, asset presence, build provenance, and regression performance. **Review:** final narrative canon, risky tool calls, release branches, legal/permission-sensitive voice work, and anything with irreversible side effects. **Learn:** traces, eval datasets, ADRs, style guides, contributor decisions, and project memory that improve later runs without silently rewriting canon. citeturn27view4turn27view5turn27view1turn33view0turn23view5turn28view4

## Dialogue and quest generation

Current evidence supports using LLMs for **first-pass content generation**, but not for direct publication of canonical quest or dialogue content. Research on character-consistent NPC dialogue shows that better results come from combining static character knowledge with dynamic memory rather than relying on prompt-only roleplay; the authors explicitly identify inconsistent character representation and limited memory retention as central problems. Separate work on quest generation finds that adding structured world knowledge improves quest quality, and recent studies of machine-readable side-quest generation show that LLMs can produce JSON-shaped quest artefacts, but still require additional validation when gameplay logic becomes more complex. citeturn14view4turn15view1turn15view2

The key lesson is that **single-prompt creativity is not enough** for a game production pipeline. A 2026 schema-governed RPG pipeline paper is especially relevant to Wasteland Forge because it argues that generated narrative content too often stays in “sandboxed or illustrative settings” rather than becoming verifiable, executable artefacts. Its proposed remedy is a knowledge-management layer that governs characters, quests, dialogue logic, and interaction rules across generation, validation, storage, and runtime use. A separate world-to-quest pipeline paper reaches a similar conclusion from another angle: individual quest artefacts may look coherent in isolation, but consistency across worlds, NPCs, and quests is not reliably enforced unless the generation process is layered and dependency-aware. citeturn14view3turn15view0

That points to a very specific authoring model for Forge. AI should generate **typed intermediate artefacts**, not final GECK/NVSE-facing content directly. In practice that means dialogue manifests, branch graphs, condition stubs, reputation check suggestions, ambient bark sets, and quest skeletons should be emitted as structured JSON or YAML under strict schemas. OpenAI’s structured outputs are directly useful here because they guarantee JSON Schema adherence and remove a large class of invalid enum/key failures. Evaluation suites then become mandatory, not optional: OpenAI’s eval guidance explicitly treats evals as the primary way to measure system reliability under model variability, and prompt engineering guidance recommends pinning model snapshots and testing behaviour whenever prompts or models change. citeturn27view4turn27view5turn27view6

Human review remains non-negotiable for final canon. The U.S. Copyright Office’s January 2025 report is relevant here because it concludes that prompts alone do **not** provide sufficient human control for authorship, and that purely AI-generated material is not protected in the same way as human-authored expression. That does not make AI useless for writing; it means Forge should treat AI-generated quest and dialogue content as *draft production material* that becomes project-authored only after meaningful human selection, editing, arrangement, and approval. In other words, AI can be the drafting engine, but it cannot be the final narrative authority. citeturn22view0

## Voice generation

Voice is the area where Wasteland Forge can gain the most visible productivity, but it is also the area with the highest legal and social risk. The current tool landscape splits fairly clearly into **local/open** and **cloud/proprietary** options. Coqui’s XTTS-v2 supports cross-language voice cloning from a short sample and advertises 17 languages at 24 kHz. OpenVoice V2 is MIT-licensed, supports multilingual voice cloning, and is free for commercial use under that licence. xVASynth, which is already familiar in Bethesda modding circles, is GPL-3.0 and explicitly positions itself as a speech synthesis app using voices from characters or voice sets from video games, with model ecosystems hosted externally. citeturn16view1turn16view2turn16view3

Those differences matter architecturally. XTTS and OpenVoice make good candidates for **optional local adapters** because they support developer-controlled generation and can fit open pipelines. xVASynth is better understood as an **external integration** rather than a core dependency: it is powerful and modding-relevant, but it sits inside a game-voice ecosystem that carries additional rights, provenance, and redistribution questions. Cloud providers such as ElevenLabs offer high-quality services with provider-level safeguards, but they also introduce service-specific terms and policy dependencies. ElevenLabs states that voice cloning is restricted by IP/safeguard policies and that generated audio can be traced back to the responsible user, which is a useful compliance feature but also a reminder that cloud voice is never a neutral dependency. citeturn16view4turn16view7

The modding-specific social layer is just as important as the technical layer. Nexus Mods’ policy does **not** ban AI-generated mod content outright, but it reserves the right to remove it after credible complaints by affected creators or rights holders. Its Submission Guidelines also require permission for copyrighted content, make uploaders responsible for legal compliance, and explicitly state that mod authors are responsible for verifying the accuracy of claims made on mod pages, including content generated or assisted by generative AI. In other words, the community platform most likely to host a Fallout project already expects the human uploader, not the tool, to carry responsibility. citeturn16view5turn36view0

The broader legal environment points in the same direction. The U.S. Copyright Office’s digital replicas report concludes that current law is insufficient and that a new federal law is needed for unauthorised digital replicas because AI enables voice and likeness replication at speed and scale. SAG-AFTRA has already built agreement frameworks around digital voice replicas that centre consent, licensing, and compensation. In Europe, the AI Act and the Commission’s code-of-practice work establish a transparency direction for AI-generated and manipulated content, including marking and labelling expectations. Taken together, that means Forge should **never** ship cloned canonical voices by default, should require explicit rights metadata for any voice model or sample set, and should make synthetic voice disclosure a first-class part of the export pipeline. citeturn21view0turn17search0turn17search1turn17search11turn18search1turn18search11

The right R005 conclusion, therefore, is not “Forge owns voice generation end-to-end.” It is “Forge owns the **voice pipeline contract**.” That contract should support multiple providers, store permissions and provenance, generate manifests for lines/lips/export steps, and refuse to treat any proprietary or rights-sensitive voice system as a hard requirement. This is the point where your earlier proposed rule — no proprietary dependency becoming a hard requirement — becomes strategically essential rather than merely ideological. citeturn16view2turn16view4turn16view5turn36view0

## Agent architecture

Wasteland Forge should adopt an **agent architecture**, but not a “swarm” architecture. The best evidence supports a small number of specialised agents operating under explicit contracts, with a deterministic orchestration layer above them. OpenAI’s Agents SDK is notable because it is MIT-licensed, provider-agnostic, and already includes the exact primitives Wasteland Forge would need: sessions, tracing, guardrails, human-in-the-loop controls, and tool integrations. LangGraph is similarly MIT-licensed and oriented toward long-running, stateful workflows with persistence, interrupt/resume patterns, and long-term memory. Both are credible building blocks. citeturn30view0turn28view0turn28view1turn28view2turn28view3

At the same time, the agent framework ecosystem is moving too quickly to justify hard-coding Wasteland Forge to any one vendor’s orchestration model. Microsoft’s AutoGen is now explicitly in maintenance mode and points new users toward Microsoft Agent Framework; Microsoft positions Agent Framework as the successor to both AutoGen and Semantic Kernel, while its Semantic Kernel orchestration features remain marked experimental. That degree of churn is a warning sign: Forge should build around an **internal agent contract** and runtime adapters, not around a single external framework as a permanent platform dependency. citeturn34view0turn30view3turn30view4

The research literature also argues against unconstrained multi-agent enthusiasm. A recent storytelling study found that a simple Writer–Editor loop can improve narrative quality over a small number of iterations, which is highly relevant for dialogue and quest drafting. But a separate 2026 study found that self-organising LLM teams often fail to match the performance of their strongest individual member because they “average away” expertise instead of deferring to it properly. The survey literature reinforces the same point: multi-agent systems need explicit structures, strategies, and coordination protocols. For Forge, the message is clear — use specialist roles and explicit handoffs, not freeform committee dialogue among bots. citeturn14view1turn14view0turn14view2

A practical Wasteland Forge design would therefore look like this in behaviour, even if the exact implementation changes later: a **Research Agent** gathers and cites evidence; a **Lore Agent** resolves canon and style constraints; a **Quest Agent** produces typed quest structures; a **Dialogue Agent** expands them into branches and bark sets; an **Asset/Voice Agent** produces manifests and provider calls; a **Validation Agent** checks schemas, provenance, permissions, and regressions; a **Documentation Agent** updates research, changelogs, and user-facing docs; and a **Release Agent** prepares artefacts but cannot publish without approval. The orchestrator owns state, approvals, and traces. No specialist agent should be allowed to merge to a protected branch, modify permissions records, or invoke destructive tools without explicit human authorisation. citeturn27view0turn27view1turn28view1turn29view0

## Coding, validation, documentation, and project memory

AI-assisted coding should be treated as **accelerated scaffolding**, not as a trusted source of correct implementation. GitHub’s own application card for Copilot agents warns that generated code may be inaccurate, insecure, semantically wrong, or a near match for public code, and explicitly says Copilot review should supplement human review rather than replace it. Academic work from 2025 and 2026 points in the same direction: code-generation quality and security remain inconsistent across languages and models, and prompt engineering alone is not a reliable cure for insecure outputs. For Wasteland Forge, AI is valuable for bootstrapping registry generators, validators, tests, build scripts, and refactors, but those outputs must flow through ordinary code review, security checks, and regression tests. citeturn24view2turn24view3turn6search0turn6search3turn6search9

That validation layer should be unusually strong, because agentic systems introduce new failure modes in addition to ordinary software bugs. OpenAI recommends input, output, and tool guardrails, plus human approvals before sensitive side effects. Its safety guidance specifically recommends structured outputs to constrain data flow between nodes, warns against injecting untrusted data into high-authority instructions, and advises keeping tool approvals on when MCP is involved. OWASP’s 2025 LLM guidance reinforces that prompt injection is intrinsic to how these systems process language, that RAG and fine-tuning do not fully solve it, and that connected tools dramatically raise the impact of failures. In Forge terms, every agent boundary should be schema-validated, every external-content ingestion step treated as hostile by default, and every tool with write/publish/delete capability routed through explicit approval policies. citeturn27view0turn27view3turn29view1turn31view0turn31view1

Documentation is one of the places where Wasteland Forge can safely automate the most. GitHub already supports automatically generated release notes, and Release Drafter-style workflows can keep draft changelogs current as pull requests are merged. For longer project memory, Markdown-in-repo plus a static documentation site is the better fit than ephemeral chat logs. MkDocs and Material for MkDocs are well-aligned with that approach because they keep docs as source-controlled Markdown, support configuration through plain YAML, and provide searchable static output. This matters because AI systems need **stable, reviewable project memory**: prompt snippets and local chats are not enough for a multi-year open-source platform. citeturn33view0turn33view1turn32view0turn32view1

The memory model itself should also be split deliberately. OpenAI sessions are a good example of **run-scoped or conversation-scoped memory** that persists context across turns. LangGraph’s long-term memory model is a better example of **project-scoped memory**, where JSON documents are stored under namespaces and keys and retrieved across sessions. Forge should mirror that separation. Short-term memory is for active agent work. Long-term memory is for research notes, registries, glossary entries, decisions, contributor conventions, and test corpora. If those are mixed together, the system will either forget too much or “remember” too much in unsafe ways. citeturn27view2turn28view4

## Governance and human oversight

R005 is not complete unless it answers how an open-source project prevents AI assistance from degrading trust. The baseline governance controls are already well understood in mainstream open-source tooling. GitHub protected branches can require pull-request reviews, dismiss stale approvals, and enforce status checks before merging. CODEOWNERS can require reviews from maintainers responsible for specific paths. Issue and pull-request templates improve the quality of incoming reports and contributions. GitHub Discussions provides a space to route support and design conversation away from code issues. Artifact attestations add cryptographically signed provenance for release artefacts and can be paired with SBOMs. citeturn23view3turn23view4turn23view5turn23view6turn23view7

The Linux kernel’s 2026 AI-contribution policy is the clearest precedent for what Wasteland Forge should copy. It says AI agents may not sign contributions; only humans can certify the DCO; the human submitter must review AI-generated code, ensure licensing compliance, and take full responsibility; and AI involvement should be disclosed with an `Assisted-by` trailer naming the tool and model. That is an excellent model because it does not ban AI, but it prevents ambiguity about authorship, accountability, or legal responsibility. For an open-source modding platform where generated assets, code, writing, and even voices may be involved, that kind of explicit disclosure is a strength rather than a burden. citeturn25view1turn8search2

For Wasteland Forge, the human oversight boundary should be explicit:

- **Safe to automate fully:** draft release notes, documentation scaffolds, schema-conforming manifests, test-case generation, trace summarisation, and low-risk refactors that stay inside well-tested modules. citeturn33view0turn27view4turn27view5
- **Always review before merge or publish:** gameplay scripts, validators, branching dialogue, quest logic, external-tool actions, generated code touching security or packaging, and all public-facing documentation or changelogs that make factual claims. citeturn24view2turn24view3turn27view0turn29view1
- **Do not automate as a final authority:** legal rights decisions, voice-clone permission decisions, canonical lore/rule changes, moderation/enforcement decisions, or release publication of rights-sensitive assets. citeturn21view0turn16view5turn36view0turn31view0

This is the right moment to formalise a project rule stronger than a generic “AI policy.” Wasteland Forge should adopt a governance principle along the lines of: **No proprietary model, provider, or hosted voice system may become a hard dependency for authoring, building, validating, or releasing the project.** The evidence for that is partly ideological, but mostly practical: the orchestration ecosystem is changing rapidly, some frameworks are already in maintenance mode, some enterprise features are explicitly experimental, and cloud providers carry changing terms and policy constraints. A stable open platform should define its own contracts and treat external AI systems as pluggable implementations. citeturn34view0turn30view3turn30view4turn16view4

## ADR-005 decision

**Recommendation: ADR-005 = C, Platform Layer.** The difference from a naïve “AI-first” answer is that the platform layer should be **governed**, **typed**, and **review-centric**. Wasteland Forge should not merely “have AI features.” It should make AI a formal subsystem with schemas, validation, approvals, traces, evals, provenance, and memory. That is the only model that fits the present state of agent tooling, software governance, and digital-replica risk. citeturn27view0turn27view1turn26view0turn25view1

In concrete terms, the R005 directory should culminate in a design package where `dialogue-generation.md`, `quest-generation.md`, `voice-generation.md`, `agents.md`, `ai-development.md`, `knowledge.md`, `governance.md`, and `human-oversight.md` all feed a single `decision-summary.md` that says the following: Forge owns the **contracts** and **controls** of AI-assisted development, while generation providers, model families, and voice engines remain replaceable adapters. That keeps the platform modern without repeating the mistake of binding the next decade of development to whichever AI framework happens to be fashionable in mid-2026. citeturn30view0turn28view0turn34view0turn30view3

The architecture that follows from this report is therefore:

Wasteland Forge should provide a core CLI, schema registry, eval suite, trace store, long-term project memory, documentation generator, release pipeline, and a runtime of **specialist agents with approvals**. It should integrate with external model and voice providers through adapters, store permissions and provenance alongside generated outputs, and require human approval at every boundary where canon, law, or irreversible side effects are involved. That is the smallest version of Forge that can still genuinely be called a platform. citeturn27view4turn27view5turn23view5turn28view4turn16view5turn36view0

## Open questions and limitations

Some important questions remain open. I did not find an authoritative benchmark comparing **XTTS, OpenVoice, xVASynth, and major cloud providers specifically on Fallout-style dry line reads, noise floor, and lip-sync suitability**, so any final provider ranking would still need hands-on testing. The **jurisdiction-specific legal treatment of voice replicas** is also still evolving, especially outside the U.S. and EU, so Forge should encode permission/provenance requirements conservatively rather than assuming a settled legal baseline. Finally, the agent-framework ecosystem is changing quickly enough that the report supports an abstraction-first design, but it does **not** justify declaring one framework the permanent winner yet. citeturn16view1turn16view2turn16view3turn21view0turn18search1turn34view0turn30view4
