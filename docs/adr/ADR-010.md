# ADR-010 - Developer Experience and CLI Workflow Model

Status: Accepted
Research classification: Documented
Source: `WasteLandForge/research/R006 Developer Experience and CLI Workflow Model for WastelandForge-deep-research-report.md`

## Decision

WastelandForge uses a small, stable, offline-first, AI-optional CLI.

The canonical command surface is:

```text
forge init
forge validate
forge capabilities list
forge capabilities scan
forge capabilities explain
forge generate
forge build
forge package
forge release verify
forge release prepare
forge release publish
forge docs
forge graph
forge explain
forge clean
forge doctor export
forge help
forge --version
```

## Consequences

- Git hooks, editor tasks, and CI workflows must be thin wrappers around the Forge CLI.
- CLI behavior must be deterministic and composable.
- Help output should be examples-first.
- Machine-facing output contracts must be stable.
- Do not introduce undocumented convenience aliases.

## Gate Impact

Gate 6 implements the first CLI skeleton. Earlier gates must preserve the
command namespace. Gate 57 implements `forge capabilities list` against the
built-in FNV catalogue while keeping `forge capabilities scan` and
`forge capabilities explain` reserved for later detector and explanation
gates. Gate 58 implements `forge capabilities scan` for explicit local path
evidence. Gate 59 implements `forge capabilities explain` for built-in
capability and provider IDs against catalogue and scan evidence. Gate 60
extends `forge capabilities scan` with `--project` requirement resolution
without adding aliases or changing the canonical command surface. Gate 61
implements the canonical `forge generate` and `forge build` commands for the
low-risk `reports` target while keeping later game-facing generators reserved.
Gate 62 adds `--target mcm-json` to `forge generate` and `forge build`
without adding aliases or changing the canonical command surface.
Gate 63 keeps the same command surface and changes only the implemented output
from a placeholder skeleton to the validated MCM Extender runtime subset.
Gate 64 keeps the same command surface while adding runtime requirements
pass-through and translation-file output to the `mcm-json` target.
Gate 65 keeps the same command surface while expanding `mcm-json` to emit
checkbox and string-toggle settings.
Gate 66 keeps the same command surface while expanding `mcm-json` to emit
keybind settings.
Gate 67 keeps the same command surface while expanding `mcm-json` to emit
header settings.
Gate 68 keeps the same command surface while expanding `mcm-json` to emit
image settings.
Gate 69 keeps the same command surface while adding validation for MCM image
asset references.
Gate 70 keeps the same command surface while expanding `mcm-json` output to
include staged referenced texture assets under their game-relative target
paths.
Gate 71 keeps the same command surface while adding `package-manifest.json` to
the `mcm-json` generate/build output.
Gate 72 keeps the same command surface while adding build-time
`dist/mcm-json/package.zip` output for the `mcm-json` build target.
Gate 73 implements the canonical `forge package` command skeleton for
`--target mcm-json` without adding aliases or implementing FOMOD packaging.
Gate 74 keeps the same command surface while adding package manifest schema
validation and archive-entry validation to the `mcm-json` package/build path.
Gate 75 keeps the same command surface while adding `install-preview.json` to
the `mcm-json` generate/build/package outputs.
Gate 76 keeps the same command surface while validating that install-preview
report against an embedded schema.
Gate 77 keeps the same command surface while adding a human-readable
install-preview summary to the `mcm-json` generate/build/package outputs.
Gate 78 keeps the same command surface while adding `package-verification.json`
to the `mcm-json` generate/build/package outputs and human/JSON CLI summaries.
Gate 79 keeps the same command surface while validating
`package-verification.json` against an embedded schema.
Gate 80 keeps the same command surface while adding `package-verification.md`
as human-readable local package verification evidence for the `mcm-json`
generate/build/package path.
