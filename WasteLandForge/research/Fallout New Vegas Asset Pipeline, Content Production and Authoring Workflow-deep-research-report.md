# Fallout New Vegas Asset Pipeline, Content Production and Authoring Workflow

## Executive findings

The Fallout: New Vegas production pipeline is not a modern “import assets into engine” workflow. It is a path-sensitive, record-driven pipeline whose centre of gravity is still the GECK, with critical support from GECK Extender, xNVSE-family runtime plugins, xEdit, NifSkope, Blender/NifTools, BSArchPro, and Mod Organizer 2. In practice, authors create or edit assets externally, wire those assets into records inside GECK or xEdit, test through MO2’s virtual filesystem, and only then package for release. That means Wasteland Forge should be designed as an orchestration layer over an existing toolchain, not as a replacement for it. citeturn28view0turn22view3turn23view0turn34view2turn23view4

The strongest technical pattern in the sources is this: development is easiest with loose files, while release quality is best with packed archives. GECK’s own guidance says assets in existing BSAs usually need to be extracted before they can be attached to forms, and recommends leaving assets loose while creating and editing a mod, then packing them into BSA for release. GECK’s BSA and packing guidance also says packed BSAs reduce loading times, memory use, stutter, and filesystem fragmentation when used correctly. citeturn26view4turn26view5turn24view1

Voice and dialogue production are the clearest examples of where Wasteland Forge can add real value. GECK can already export quest dialogue and calculate required voice assets, while lip generation requires a precise folder structure, specific audio properties, and extra processing files that do not ship with the New Vegas GECK. Those are exactly the kinds of brittle, repetitive steps that benefit from generation, validation, and build automation. citeturn24view5turn24view2

The recommended decision for **ADR-004** is therefore **C: Extensive ownership**, but with a hard boundary: Wasteland Forge should own **generation, validation, packaging, release automation, and workflow integration**, while deliberately **not** replacing Blender, NifSkope, GECK, xEdit, MO2, xNVSE, UIO, or MCM. In other words, Forge should become the authoring platform around the pipeline, not the substitute for the pipeline. citeturn23view3turn33view0turn27view0turn27view1turn31view0

## Development environment and workflow backbone

The current FNV workflow is built around a layered stack rather than a single editor. GECK remains the canonical editor for forms, quests, dialogue, terminals, and world data, but GECK Extender materially changes how usable that editor is by enlarging script-related windows, doubling script size limits, restoring warning and error messages, improving plugin loading speed, increasing the editor’s file-handle limit from 512 to 2048, and disabling the dangerous “Recompile All” button. Those changes are not cosmetic; they directly affect how large projects can be authored and debugged. citeturn28view0

On the runtime side, xNVSE expands scripting and engine capabilities without modifying the executable on disk, and current xNVSE development is explicitly focused on scripting quality-of-life improvements. Recent xNVSE releases added inline expressions, lambdas, chained dot syntax, inline variable declarations, new scheduling-style functions, a script decompiler, and load-time/script-compilation optimisations. For content production, that matters because generated runtime support code can now be more expressive and easier to maintain than older NVSE-era scripts. citeturn22view3turn29view0

Hot Reload is especially important for authoring workflow because it lets scripts be updated live while the game is open, generates editable script files on disk, supports external text editors, and removes one of the largest iteration bottlenecks in FNV modding: restarting the game after every script change. GECK Wiki’s scripting guidance explicitly recommends Hot Reload and external text editors for authors, which means the ecosystem has already moved beyond the GECK script window as the only reasonable editing environment. citeturn27view4turn18search2turn18search8

MO2 is the de facto workflow hub for serious setups because it keeps the game folder clean, exposes file conflicts, supports portable instances, and sits on top of USVFS, a process-local virtual filesystem that makes redirected files appear real to selected applications. MO2’s own plugin API also exposes profiles, virtual file trees, file origins, download management, save-game interfaces, diagnostics, and tool/plugin extension points. That is highly relevant to Wasteland Forge: it means Forge can integrate into the modder’s existing workspace instead of requiring a new workspace. citeturn23view3turn23view4turn23view2turn32view0turn33view0

xEdit completes the backbone. Its own documentation is explicit that xEdit’s main jobs are conflict detection, resolution, cleaning, error checking, and module inspection, not primary content creation. That division of labour is important: GECK is still where content is authored, while xEdit is where content is inspected, patched, and validated. Wasteland Forge should preserve that separation instead of blurring it. citeturn23view0turn23view1turn30view2

## Mesh, texture, audio, animation and effects pipelines

For meshes, the engine is still built around **NIF** assets, with related files such as **KF** for animations and **RDT** for ragdoll data. GECK’s BSA documentation lists NIF, RDT, KF, DDS, WAV, OGG, and supporting files as first-class game assets, while GECK’s NIF-related pages warn that not every registered NIF block is actually safe or functional in New Vegas. In practical terms, the pipeline is conservative: use supported blocks, supported shader properties, and engine-compatible paths, because invalid structure can cause missing visuals or crashes. citeturn25view0turn39search3turn39search13turn39search2

For creation and editing, the community still relies on **Blender plus NifTools** and **NifSkope**, but the sources show a clear maturity gap. The official Blender NifTools documentation literally warns that the documentation is incomplete and still a work in progress; the main addon supports NIF and KF import/export, but the project itself says it is still working towards a full v1.0.0. A dedicated Fallout New Vegas fork exists specifically to make FNV animation export possible, which is strong evidence that the official general-purpose addon is not the whole story for New Vegas-specific work. NifSkope, meanwhile, is positioned as a viewer and editor for NIF rather than a full creation tool. citeturn34view0turn34view1turn34view3turn34view2

Textures are largely **DDS-based** and are often mediated through **Texture Set** records rather than by editing the mesh for every variant. GECK’s Texture Set documentation lays out the expected map types and common suffix conventions: diffuse, normal/gloss, environment mask, glow, height, and environment maps. That makes texture validation a particularly suitable target for Forge, because many errors are deterministic: wrong suffixes, missing normal maps, broken material references, or invalid texture paths. citeturn24view7turn39search12

Audio is split between ordinary sound forms and special-case dialogue/radio behaviour. GECK’s Sound form is used for most game audio apart from most actor dialogue, can be called from scripts, can be associated via NIF or KF, and exposes attenuation and playback settings. Radio content has even stricter requirements: GECK’s radio guidance says Pip-Boy music should be WAV or MP3 in 32-bit float, but world/radio speaker playback also needs a separate `_mono` asset, with MP3 disallowed for that mono copy. GECK’s BSA documentation further warns that MP3 will not work inside New Vegas BSAs and that audio will not play if the BSA is compressed, so audio packaging cannot be treated like ordinary texture packaging. citeturn25view3turn35search1turn35search0

Animation is still heavily legacy-shaped. Vanilla animation assets are **KF files** stored under expected character paths, with special directories such as `meshes\characters\_male\specialanims` and strict handling through animation groups. The vanilla idle system expects KF files in `IdleAnims` beneath the relevant skeleton directory, and only one animation per animation group can play at a time. kNVSE exists because the vanilla animation system is limited; curated FNV guides describe it as a resource that expands and improves the game’s animation system, and the mod itself is widely used to support custom weapon and movement animations without overwriting other assets. GECK’s own BSA packing advice says **do not pack KF files** unless you know the mod does not rely on kNVSE, which is a very strong signal that animation packaging rules need capability-aware tooling. citeturn24view3turn24view4turn38view1turn8search11turn26view0

Effects and visual feedback are authorable, but they are still record-centric rather than node-graph-centric. **EffectShader**, **ImageSpace Modifiers**, **Explosion**, weather/image-space links, and related forms are all configured through GECK records. This means Wasteland Forge does not need to invent a new effects editor to add value. It can instead generate repeatable templates, schemas, and validations around record combinations that are already known to work. citeturn25view4turn25view5turn25view6

## Dialogue, voice and documentation assets

Dialogue production in New Vegas is tightly coupled to quests and records. GECK’s Quest Data tab can **export quest dialogue** and **calculate voice assets** for a quest, while dialogue info records support per-line conditions, optional result scripts, prompt text, speaker restrictions, and alternate sound handling. GECK Wiki also notes that explicitly selecting a speaker acts like a `GetIsID` restriction when dialogue is exported, which means dialogue export is more structured than it first appears. For Wasteland Forge, this is an opportunity: dialogue manifests, per-voice worklists, and CI checks can be generated from the record layer rather than maintained manually. citeturn24view5turn36search0turn36search1

The voice pipeline is brittle enough that it should be treated as a first-class build problem. GECK’s Facial Animation page says lip generation needs both source WAV files and OGG files created from those WAVs; for New Vegas, the OGG files are expected at **24 kHz**, average **64 kbps** variable bitrate, and **mono**. Voice assets must sit under `Data\Sound\Voice\[PluginName]\[VoiceType]`, and the files must be named after valid dialogue in the master file or lip files will not be created. The same page also says New Vegas GECK does **not** ship with the processing files required for lip generation and that authors need to copy them from the Skyrim or Fallout 4 Creation Kit into `Data\sound\voice\processing\`. That is exactly the sort of hidden prerequisite that causes broken releases and wasted iteration time. citeturn24view2turn36search2

This voice evidence leads to a clear design implication: Wasteland Forge should own a **voice build system**. At minimum, that system should export dialogue manifests, map lines to the correct voice-type folders, verify that WAV and OGG pairs exist, check sample rate/channel constraints, detect missing processing assets for lip generation, and optionally call external encoders such as FFmpeg or Audacity-compatible workflows. The primary sources do not provide an official batch compiler, but they do provide enough structure to justify automation around the official engine expectations. citeturn24view2turn24view5

Terminals, holotapes, notes, and books fit the same pattern. GECK documents terminals as world objects that can contain notes, gate access via passwords, and run arbitrary scripted functionality through menus and submenus. Form type documentation shows **TERM**, **BOOK**, and **NOTE** are all ordinary form types in the engine. That means “codex-style” content in Wasteland Forge does not need a bespoke runtime data model first; it can compile to the same terminal/note/book primitives the engine already understands. citeturn24view6turn37search2turn37search1

On the UI side, the ecosystem already contains reusable infrastructure. **MCM** adds a shared pause-menu configuration surface and deliberately avoids forcing a master dependency on mods that use it, while **MCM Extender** adds JSON-driven, script-free menu generation, automatic INI and variable handling, and even allows a dedicated MCM without an ESM/ESP. **UIO** is expressly designed to detect, resolve, and prevent UI/HUD extension conflicts. The implication is straightforward: if Wasteland Forge wants user-facing configuration or documentation surfaces, it should generate into MCM/UIO-compatible formats instead of replacing those frameworks. citeturn27view2turn27view1turn27view0

## Packaging, distribution, testing and validation

The release pipeline in New Vegas is built around a mixture of **ESP/ESM plugins**, **BSA archives**, **loose files**, and mod-manager packaging formats such as **FOMOD**. GECK’s BSA documentation says the engine loads BSAs in plugin-associated order, but unlike plugin override rules, **the first BSA loaded wins file conflicts**, unless loose files override via archive invalidation. It also notes that multiple BSAs can be associated with a single plugin as long as naming conventions are respected. That inversion of normal plugin expectations is a major source of packaging mistakes, and it is a compelling target for automated validation. citeturn25view0turn26view5

The official guidance is also highly specific about what should and should not be packed. GECK’s packing tutorial recommends packing DDS, NIF, WAV, OGG, EGM, EGT, LIP, LST, and SPT, but advises against packing MP3, XML, JSON, INI, and—critically—KF where kNVSE may be involved. BSA notes add that audio should be kept in **uncompressed** BSAs, MP3 should not be put into New Vegas BSAs at all, and packed NIF paths must use backslashes rather than forward slashes. These are all deterministic packaging rules that a release tool can enforce automatically. citeturn26view0turn35search0

MO2 is the dominant distribution and test harness in curated workflows. Viva New Vegas recommends a portable MO2 instance outside Program Files, uses MO2 for nearly all managed content, and distinguishes clearly between root-folder utilities such as xNVSE and managed mods installed through MO2. MO2’s own plugin system supports installers, tools, diagnostics, file mappings, and game-specific extensions, while its API can create mods, inspect the virtual file tree, and report file origins. In other words, a Wasteland Forge plugin for MO2 is not speculative; the platform already exposes the primitives needed to create one. citeturn23view3turn38view1turn32view0turn33view0

For validation, xEdit remains the strongest existing foundation. Its documentation covers conflict detection, error checking, unresolved references, deleted references, deleted navmeshes, circular levelled lists, master sorting, and cleaning. It also has an **Assets Manager** that can check used assets and copy assets used by a plugin, but its own documentation explicitly says that implicit assets are **not** fully covered, listing voice files, facegen files, worldspace LOD, animations, and race models as examples the script does not process for you. That limitation is important: it shows precisely where Wasteland Forge can add complementary validation instead of duplicating xEdit. citeturn23view1turn31view2turn31view3turn31view0

Testing, then, should be framed as layered rather than singular. xEdit should remain the authority for plugin and record integrity; MO2 should remain the authority for profile-based installation, conflict visibility, and reproducible test environments; GECK/GECK Extender should remain the authoring surface; and Wasteland Forge should add the missing production-grade checks around assets, manifests, packaging, and cross-tool consistency. That division of labour aligns with the tools’ own design goals and avoids rebuilding mature infrastructure for no gain. citeturn23view0turn23view3turn28view0turn31view0

## Implications for Wasteland Forge and ADR-004

The evidence supports a very clear product boundary. Wasteland Forge should **own** the parts of the pipeline that are repetitive, brittle, derivable, and cross-cutting: dialogue export/import manifests, voice worklists, asset registries, missing-file checks, path linting, BSA packing recipes, release assembly, documentation generation, provenance metadata, and integration glue for MO2/xEdit/GECK-centric workflows. Those are the areas where the ecosystem is fragmented and where the official tools mostly provide primitives rather than a complete production system. citeturn24view5turn24view2turn31view0turn32view0

Wasteland Forge should **integrate with** MO2, xEdit, GECK Extender, xNVSE, and runtime libraries such as UIO and MCM Extender. MO2’s API is rich enough to support profile-aware tool plugins, guided diagnostics, and virtual-file inspection. xEdit already solves plugin-level conflict and error analysis. MCM Extender already solves JSON-driven configuration UI. UIO already solves multi-mod UI extension coexistence. There is no strategic upside in replacing any of these. citeturn32view0turn33view0turn23view1turn27view1turn27view0

Wasteland Forge should **not own** 3D authoring, audio editing, low-level NIF editing, or raw plugin editing. The source base around Blender/NifTools and NifSkope shows that those edit domains are specialised, external, and already tool-rich, even if imperfect. GECK and xEdit remain the native places where records are authored and inspected. A successful Forge should therefore act more like a build system and developer platform than like a replacement editor. citeturn34view0turn34view1turn34view2turn23view0turn28view0

That yields the following practical ownership model for **ADR-004**:

- **Forge should generate** dialogue manifests, voice manifests, terminal/note content manifests, MCM Extender JSON, packaging manifests, and release metadata. citeturn24view5turn27view1
- **Forge should validate** missing meshes, missing textures, invalid texture/path conventions, missing voice assets, wrong audio formats, broken BSA packing rules, unresolved file references beyond xEdit’s explicit asset scan, and capability-sensitive packaging rules such as kNVSE/KF handling. citeturn24view7turn24view2turn35search0turn31view0
- **Forge should automate** lip-generation prerequisites, per-quest voice build steps, BSA assembly, MO2 test-profile setup, and release bundles assembled from known-good outputs. citeturn24view2turn26view5turn32view0
- **Forge should leave external** Blender, NifSkope, DAWs/audio editors, GECK record editing, xEdit conflict resolution, and runtime framework ownership. citeturn34view2turn34view1turn23view0turn27view0turn27view1

Taken together, the report supports **ADR-004 = C**, but in a specific sense: **Extensive ownership of the production layer, not extensive ownership of the creative tool layer**. If Forge tries to become a modelling suite, an audio editor, or a replacement mod manager, it will fail strategically. If it becomes the reproducible build-and-validation platform wrapped around those tools, it fills one of the clearest gaps in the New Vegas ecosystem. citeturn26view5turn31view0turn32view0turn33view0

## Open questions and limitations

This research was strongest where primary documentation exists: GECK, xNVSE, MO2, xEdit, and NifTools. It is therefore highly confident about record wiring, voice/lip requirements, BSA rules, MO2 integration capability, and xEdit’s validation envelope. It is less complete on the current state of third-party AI voice generation, modern animation authoring tutorials, and the exact production practices used by large contemporary quest-mod teams, because those areas are more fragmented and often documented informally rather than in canonical technical references. citeturn24view2turn23view0turn32view0turn34view0

The most important open questions for a follow-on implementation phase are these. First, whether Forge should invoke existing packers such as BSArchPro/BSArch directly or emit manifests for human-invoked pack steps. Second, how far Forge should go in automating lip generation on build agents, given the need for processing assets copied from another Creation Kit. Third, whether an MO2 plugin, a standalone CLI, or both should be the first integration surface. The evidence already points toward “both”, but this report stops short of prescribing the rollout order. citeturn24view1turn24view2turn32view0turn33view0
