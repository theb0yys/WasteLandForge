# ADR-012 - Premium Windows App Shell

Status: Accepted
Research classification: Inferred from documented platform, CLI, release, and
dependency decisions plus user-supplied licensed Heat 1.1.8 ownership evidence
Source:
`WasteLandForge/research/Wasteland Forge Platform Architecture & System Design-deep-research-report.md`,
`WasteLandForge/research/R006 Developer Experience and CLI Workflow Model for WastelandForge-deep-research-report.md`,
`WasteLandForge/research/WastelandForge Validation Testing CI Release and Governance-deep-research-report.md`,
Unity Asset Store Terms/EULA, Heat 1.1.8 readme, and user-provided ownership
evidence

## Decision

WastelandForge will provide a premium native Windows desktop app shell named
`WastelandForge.exe`.

The accepted implementation target is .NET/WPF. The app shell uses the licensed
Heat - Complete Modern UI 1.1.8 kit as the visual direction and optional
licensed build input, but it is not a Unity Player app and does not require the
Unity runtime. Heat source assets remain outside repository source control.

The app shell does not replace the Forge CLI or deterministic Forge core. It is
a presentation and orchestration layer that runs `forge.exe` as the backend
worker and consumes machine-readable output.

The first backend bridge is:

```text
forge.exe --version
forge.exe capabilities list --format json
forge.exe validate <project-root> --format json
```

The GUI consumes stable machine-readable Forge output. Human console text is
allowed in advanced logs only.

## Consequences

- `forge.exe` remains the stable automation interface for CI, scripts, editor
  tasks, and power users.
- The app shell is not a second source of validation, build, capability, or
  release truth.
- Canonical project truth remains versioned YAML/JSON source contracts in the
  repository.
- The app shell must preserve offline-first and AI-optional correctness.
- The app shell must not introduce undocumented Forge command aliases.
- Unity project files, Unity generated output, and Unity Player builds are not
  part of the accepted app-shell implementation.
- Heat source assets must not be committed to the public repository or
  redistributed as a raw reusable asset pack.
- Heat-derived app assets may be embedded into local app builds only after the
  license and attribution boundary is recorded.
- Heat is not a hard requirement for WastelandForge core contribution,
  validation, build, or release verification.

## First MVP Surface

The first premium app shell includes:

- branded splash/application chrome,
- project selector,
- Doctor and capability dashboard,
- validation report view,
- advanced log panel,
- local settings surface for project, game root, Data root, and tool paths.

The app may expose terminal-equivalent details in advanced views, but raw
console output must not be the first-run product experience.

## Asset And License Boundary

The Heat kit is treated as a licensed local asset input for the WPF app-shell
build, not as repository source truth.

Minimum audit checks:

- record Unity Asset Store license tier and contributor seat coverage,
- confirm Restricted Asset status before public release,
- record third-party notices required by the Heat readme,
- handle CC BY 3.0 controller graphic attribution if those graphics ship,
- avoid AI/ML training, dataset use, scraping, or asset extraction workflows,
- keep end users from receiving the Heat kit as a reusable source asset pack.

## Gate Impact

Gate 312 remains routed to `forge init` project scaffold planning. Gate 313 is
the premium Windows app-shell planning lane. Gate 314 records the Heat license
and WPF asset boundary.

Later app-shell gates should cover:

- WPF project hardening,
- app-to-CLI process bridge expansion,
- JSON report contracts consumed by the app,
- first-run setup wizard,
- Doctor/capability dashboard,
- validation report view,
- installer packaging,
- signing, update, and release evidence.

## Open Checks

- Installer technology and update channel.
- Code signing and release provenance model for the Windows app.
- CI strategy for desktop builds without making Heat a hard dependency of core
  CLI validation.
- Exact Heat attribution bundle and third-party notice text.
- Final release packaging rule for embedded Heat-derived assets.
