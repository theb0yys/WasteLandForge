# Fallout New Vegas Tooling Ecosystem and Modding Landscape

## Scope and method

This report evaluates the Fallout: New Vegas modding ecosystem as it exists on 9 June 2026, with evidence weighted toward primary project documentation and source repositories, then cross-checked against the dominant guide ecosystems and current distribution pages. In practice, that means the GECK Wiki, xNVSE, xEdit, Mod Organizer 2, GECK Extender, and directly maintained GitHub repositories carry the most weight, while Viva New Vegas, The Best of Times, Nexus project pages, and selected TTW support material are used to confirm how those tools are actually adopted and supported in the field. citeturn32view1turn16view0turn16view1turn16view2turn19view0turn32view0turn32view3

The purpose is not to compile an exhaustive museum catalogue of every FNV utility ever published. It is to answer a more strategic question for Wasteland Forge: which parts of the ecosystem are already mature and socially entrenched, which parts are still fragmented, and where a new platform can create leverage without duplicating tools that the community already trusts. The source set strongly suggests that the modern New Vegas ecosystem is not a blank slate; it is a layered platform made of editor extensions, script extenders, guide infrastructure, mod managers, conflict-analysis tools, UI frameworks, and highly opinionated support practices. citeturn17view0turn18view0turn20search0turn24view2turn32view0turn34view1

## Executive findings

The first high-level finding is that the ecosystem is active, not archival. xNVSE’s GitHub repository lists a latest release of **6.4.8** on **25 May 2026**; JohnnyGuitar NVSE lists **5.28** on **30 May 2026**; GECK Extender was updated on Nexus on **30 May 2026**; and Viva New Vegas published guide updates in March 2026 covering xNVSE, ShowOff, Crash Logger, and other core utilities. Even long-lived framework mods such as MCM are still receiving packaging and installer updates, including a newer XML-based FOMOD in December 2025. In other words, New Vegas modding is old, but its infrastructure is still moving. citeturn16view0turn24view1turn19view1turn5search4turn29search1

The second finding is that many of the “platform” problems Wasteland Forge might otherwise try to solve are already handled by existing tools. MO2 already owns mod isolation, profile management, and execution context; xEdit already owns plugin inspection, conflict detection, cleaning, and patch-oriented workflows; xNVSE and its plugin ecosystem already provide a deeply extended runtime API; GECK Extender makes the editor substantially more usable; UIO mitigates UI/HUD XML conflicts; MCM and MCM Extender provide an in-game configuration surface; and kNVSE materially expands the game’s animation system. That is too much existing capability to justify a replacement strategy. citeturn18view0turn17view0turn17view1turn19view0turn24view2turn28search2turn28search0turn21search0

The third finding is that the ecosystem’s weaknesses are less about missing raw capability and more about fragmentation. Knowledge is split between the community GECK Wiki, GitHub wikis, GitHub readmes, Nexus descriptions, and guide sites; support is increasingly Discord-first and human-mediated; validation is strong for plugin conflicts and crash logging but weaker as a unified end-to-end developer workflow; and mainstream guides emphasise prevention, clean installs, and new saves more than they provide a modern save-forensics pipeline. That makes the unsolved problem look like **orchestration, consistency, capability detection, code generation, cross-tool validation, and documentation cohesion**, rather than “we need a new xEdit” or “we need a new mod manager.” That is an inference from the evidence, but it is a well-supported one. citeturn32view1turn17view0turn17view2turn34view1turn12search3turn35search1

Taken together, the evidence points toward **ADR-002 outcome C**: Wasteland Forge should become a **developer platform that orchestrates existing tools**, with selective runtime components only where the current runtime stack cannot express the required behaviour safely or ergonomically. Outcome A would duplicate mature infrastructure. Outcome B would be too small, because the real opportunity is not just “integration” in the abstract; it is codifying institutional knowledge and turning a fragmented toolchain into a repeatable platform. citeturn16view0turn16view1turn16view2turn19view0turn24view2turn32view0turn34view1

## Core toolchain and day-to-day workflow

For content authoring, the canonical editor is still the GECK, but serious work now assumes **GECK Extender** rather than stock GECK. GECK Extender’s current documentation and mod page show that it fixes editor crashes and memory leaks, improves loading and UI speed, doubles the script size limit, restores warnings and compilation feedback, allows ESMs as active files, preserves ESP masters, improves LOD workflows, and disables hazardous editor behaviours such as “Recompile All.” This is not a minor plugin; it is effectively the modern baseline for using the editor without fighting it. citeturn19view0turn19view1

For plugin analysis, **xEdit/FNVEdit** is the central inspection and validation layer. Its official docs present it as an advanced module viewer/editor and conflict detector, and explicitly document conflict detection, cleaning, merged or patch plugins, reachability scanning, form-error checks, and other functions that mod authors use to make lists cooperate. The docs are particularly clear that conflict resolution is fundamentally a load-order-and-overrides problem, and that xEdit exists to expose which overrides are desirable, which are destructive, and where manual patching is required. For Wasteland Forge, that means plugin intelligence is a solved problem only if Forge integrates with xEdit’s worldview rather than trying to invent a different one. citeturn17view0turn17view1turn17view2

For environment and installation management, **Mod Organizer 2** is more than a downloader. The current MO2 and Viva New Vegas documentation describe a virtual filesystem model, safe install/uninstall, multiple profiles, and clean separation from the base game; they also point out the trade-offs, notably that tools only “see” mods when launched through MO2 and that large numbers of loose files can introduce overhead. Viva New Vegas and TTW guidance both make this operational: GECK, xEdit, and other tools are expected to be run through MO2 so that the correct virtualised mod state is visible. This is a crucial architectural constraint for Forge: any desktop tooling that inspects a user’s project state must understand MO2 profiles, profile-specific INIs, and MO2’s launch context. citeturn18view0turn18view1turn34view0turn7search20

The install workflow is also sharply divided between **root mods** and **managed mods**. xNVSE itself is installed to the game root, not through MO2; the 4GB Patcher and Epic Games patcher are root-level tools; the BSA Decompressor is an external utility; while most other mods are intended for MO2-managed installation. Viva New Vegas preserves that split even when it offers Wabbajack automation, which shows that the automated path still rides on top of the same underlying rules instead of replacing them. Wasteland Forge should therefore assume that a “project” spans at least three technical surfaces: the game root, the MO2 profile, and the managed modlist. citeturn16view0turn29search2turn35search1turn11search9turn29search4

Asset authoring and packaging are similarly specialised. **NifSkope** remains the standard NIF inspector/editor; **BSA Browser** provides archive browsing, extraction, and comparison; the GECK Wiki’s BSA documentation notes that BSA precedence is **first-loaded-wins**, the opposite of plugin conflict behaviour, and that BSA packaging can improve memory use and performance; and **Blender/NifTools** support exists, but the general Blender NifTools docs still describe themselves as incomplete while FNV animation export depends on a dedicated fork with game-specific caveats. In practice, the art pipeline works, but it is not streamlined enough that Wasteland Forge should try to assume a uniform modern DCC workflow. Forge can validate paths and packaging rules here; it should not attempt to replace NifSkope or the NIF export toolchain. citeturn25view0turn25view4turn25view3turn25view1turn25view2

## Runtime frameworks and shared services

The runtime base layer is **xNVSE**. The GECK Wiki describes NVSE as a plugin and loader system that adds functions and allows plugins to hook into the engine, while the xNVSE repository presents a modernised, actively released continuation with source, developer notes, example plugin code, and packaging scripts. Most importantly for architectural scope, xNVSE’s own developer guide says that if a feature can be done in script, a plugin usually is **not** needed; scripts are fast enough for most cases and are easier to maintain, while DLL plugins are more complex and can introduce crashes or corruption if written carelessly. That is a rare case where the ecosystem’s primary runtime project is directly telling Forge how conservative it should be about native code. citeturn28search3turn16view0turn30view1

xNVSE is no longer just a loader and a bag of opcodes. Its recent “What’s New” documentation shows a substantial evolution of the scripting model: inline expressions, lambdas, richer expression compilation, better compile-time support, and a plugin-side event framework via `NVSEEventInterface` for custom event creation and dispatch. Those features put a lot more expressive power into the script layer and reduce the need for native code for orchestration or glue logic. If Forge wants quest registries, dialogue buses, or declarative reactions, there is already a much more capable scripting substrate to target than “old GECK script plus hacks.” citeturn31view3turn31view1

On top of xNVSE, **JIP LN NVSE** is still the single largest capability multiplier. Official material describes it as adding **1000+** script functions plus engine fixes and restored features, and the GECK Wiki explicitly highlights **JIP Script Runner**, which allows scripts to be executed without an ESP. JIP’s own event-handler catalogue spans dozens of event types. At the same time, the existence of **JIP PP LN** as a continuation fork means Forge should not hard-code a single “JIP forever” assumption; the safer pattern is capability detection and graceful degradation. Conveniently, the ecosystem already exposes that pattern through functions like `GetPluginVersion` and `IsPluginInstalled`. citeturn22search4turn20search0turn20search1turn22search3turn9search16turn21search15

Around xNVSE and JIP sits a mature service ecosystem. **JohnnyGuitar NVSE** adds functions, features, engine fixes, and its own event-handler family. **ShowOff** adds further functions, event handlers, cached-file APIs, and timer systems, and its documentation even recommends shipping PDBs so crash loggers can produce more precise output. **kNVSE** extends the animation system to support custom weapon and movement animations, and a separate JSON generator exists to help authors mass-produce kNVSE configuration. **SUP NVSE** adds HUD-bar and UI-related functions, but its GitHub repository is visibly looser: no formal GitHub releases, and the readme says the latest source code lives in archived RARs rather than a current branch. For Forge, that is a useful maturity signal: not every extender is equally process-stable, even if the runtime capability is valuable. citeturn24view1turn20search2turn24view3turn20search3turn20search7turn20search16turn21search0turn21search1turn24view4

The framework layer then turns those runtime APIs into shared conventions. **MCM** provides a common in-game settings surface. **MCM Extender** pushes that toward richer, script-free, and ScriptRunner-aware menus. **UIO** manages HUD and XML extensions so multiple UI mods can coexist. **hNVSE** automatically merges region lists at runtime to eliminate compatibility patches for a whole class of worldspace conflicts. These are exactly the sorts of “horizontal” services that a new framework might be tempted to recreate, but the ecosystem already has them. The right move for Wasteland Forge is to treat them as baseline services and generate or validate against them where possible. citeturn28search2turn28search0turn28search4turn24view2turn9search15turn27search1turn27search2

## Open-source operations, validation, and documentation

The strongest New Vegas projects increasingly resemble conventional software projects. **xNVSE** uses GitHub issues, pull requests, release tags, repository workflows, and a contributor/developer guide with an explicit plugin-development support channel. **MO2** is structurally even more mature: its main repository exposes a `.github` directory, CMake and vcpkg configuration, and a large constellation of related repositories for game support, installers, Python plugins, previewers, script-extender checks, and USVFS. **xEdit** also uses GitHub issues and source control, but keeps most of its formal user/developer guidance in a dedicated documentation site rather than in issue threads. This matters because it tells Forge where reliable integration points are likely to exist: in repositories, release tags, documented build systems, and known issue trackers. citeturn16view0turn30view1turn37view1turn37view3turn16view1turn17view5

The guide ecosystems are also now bona fide products. **Viva New Vegas** and **The Best of Times** are GitHub-backed, MIT-licensed repositories with public issue trackers, public sites, Discord support, changelogs, and explicit links to further resources; VNV additionally offers a Wabbajack route for automated installation. That means documentation, automation, and support policy have already become part of the practical tooling platform, not merely “community extras.” A Forge that ignores guide infrastructure would miss one of the most important layers in the real ecosystem. citeturn16view3turn16view4turn32view2turn32view3turn11search9

Validation is strong, but localised. **xEdit** handles plugin conflicts, patch plugins, cleaning, reachability, and error checking. **MO2** exposes profile exports and logs. **Crash Logger** and **Yvile’s Crash Logger** capture raw crash data. **RuntimeScriptProfiler** measures script cost, and an **MO2 plugin** now exists to visualise those profiler logs. Viva New Vegas also includes a **Utilities Checker** to validate foundational runtime dependencies. So the ecosystem does contain diagnostics; what it lacks is a unified, project-centric validation surface that spans plugin state, runtime dependency state, assets, packaging, and generated framework code in one place. That final sentence is an inference, but it is exactly what the existing tool division implies. citeturn17view0turn17view1turn17view2turn34view0turn12search0turn15search0turn14search3turn35search1

The documentation layer is broad and current, but fragmented. The **community GECK Wiki** explicitly presents itself as a living help file run by the community and maintained by NVSE modders, and it now indexes not just stock GECK material but xNVSE, JIP, JohnnyGuitar, ShowOff, MCM, kNVSE, SUP, Hot Reload, and related tools. At the same time, xNVSE mixes GitHub wiki material with repo docs; JohnnyGuitar and ShowOff send users back to the GECK Wiki for function documentation; Viva curates external resources; and NifTools openly states that its Blender documentation is incomplete. That fragmentation is not a fatal problem for an expert mod author, but it is a strong argument for Forge to act as a documentation aggregator and capability map. citeturn32view1turn16view0turn24view1turn24view3turn32view0turn25view1

Community operations are increasingly **Discord-first**, **Windows-first**, and **guide-opinionated**. xNVSE, MO2, ModdingLinked, NifTools, and TTW all point users to Discord for support or collaboration. TTW’s forum is now read-only and directs people to Discord. xEdit explicitly says its GitHub tracker is for bugs and feature requests, not general help. VNV’s FAQ routes unresolved troubleshooting to Discord, treats MO2 as the only supported manager for guide support, warns against reusing saves from different mod setups, and does not officially support Linux. This is a workable ecosystem for humans, but it reinforces the case that Forge’s job is not replacing communities; it is reducing the amount of tribal knowledge a project needs before it can become productive. citeturn10search4turn16view2turn10search6turn25view5turn10search11turn16view1turn34view1

## What Wasteland Forge should own

The evidence supports **ADR-002 outcome C**: **Wasteland Forge should become a developer platform that orchestrates existing tools and frameworks, while reserving runtime code for the comparatively small set of problems that genuinely require engine hooks or shared in-game services.** Outcome A would waste years rebuilding battle-tested infrastructure. Outcome B would leave too much value on the table, because the ecosystem’s hardest remaining problems are not single-tool problems; they are coordination and consistency problems across multiple mature tools. citeturn16view0turn16view1turn16view2turn19view0turn24view2turn32view0turn34view1

- **Integrate, do not replace:** GECK plus GECK Extender for data authoring, xEdit/FNVEdit for plugin inspection and conflict work, MO2 for environment and profile management, NifSkope/BSA tools for assets, and the guide ecosystems for install reality and support conventions. Those tools already own the community’s trust, vocabulary, and day-to-day workflows. citeturn19view0turn17view0turn18view0turn25view0turn25view4turn32view2turn32view3

- **Build against the runtime stack rather than over it:** xNVSE, JIP LN or JIP PP LN, JohnnyGuitar, ShowOff, kNVSE, UIO, MCM Extender, and hNVSE already form a service layer for scripting, events, UI, animation, and interoperability. Forge should target them with capability-aware generation and runtime detection, using existing conventions like `IsPluginInstalled` and `GetPluginVersion` rather than inventing a separate dependency model inside the game. citeturn30view1turn22search4turn22search3turn24view1turn24view3turn21search0turn24view2turn28search0turn27search2turn9search16turn21search15

- **Own the unsolved project layer:** project scaffolding, registry and manifest generation for quests/dialogue/reputation systems, capability maps, project-wide validation, asset-path linting, compatibility metadata, documentation synthesis, release templates, and cross-tool diagnostics. This is the layer the surveyed ecosystem repeatedly leaves to guides, Discord conversations, manual xEdit work, or project-specific scripts. That conclusion is an inference from the evidence, but it is exactly where the current fragmentation leaves room for leverage. citeturn17view0turn32view1turn32view0turn34view1turn12search3turn35search1

- **Treat save safety as guardrails rather than full-blown save editing at first:** mainstream modern guidance is dominated by prevention — clean installs, profile-specific saves, no save reuse across different setups, no “exit to main menu then start a new game” patterns — rather than by a richly maintained save-diagnostics ecosystem. Forge can add pre-flight checks, setup fingerprinting, dependency verification, and save-compatibility warnings before it tries to become a forensic save tool. citeturn34view1turn35search1turn13search16

- **Avoid becoming a new mod manager, a new plugin editor, a new mesh editor, or a new full script extender.** The ecosystem already has mature answers in those spaces, including some with explicit contributor paths, multi-repo architectures, release engineering, and extensive docs. Replacing them would be strategically expensive and socially uphill. citeturn16view0turn16view1turn16view2turn25view5turn30view1

A practical reading of ADR-002, then, is this: **Forge should orchestrate, validate, document, and generate — not replace mature ecosystem tools.** It can still have runtime pieces, but those runtime pieces should be thin, capability-aware, and justified by clear engine-level needs. That aligns both with the maturity of the FNV ecosystem and with xNVSE’s own guidance that native plugins should be the exception, not the default. citeturn30view1turn31view1turn24view2turn28search0

The most important open technical questions after this report are therefore narrower than “what tooling do we build?” They are: whether Forge targets **JIP LN**, **JIP PP LN**, or a capability-detected abstraction over both; whether MO2 integration should be a first-party plugin, a companion integration, or both; and how much automated save-aware validation can be achieved without bespoke runtime instrumentation. Those questions are now downstream of a clearer strategic answer: New Vegas already has an ecosystem platform, but it does **not** yet have a coherent project platform. That is the space Wasteland Forge should occupy. citeturn22search3turn21search15turn18view2turn37view3turn34view1
